# 支柱6：组织能力演进 (Organizational Evolution)

> 从个人玩法走向团队资产,建立持续改进的组织能力

---

## 一、核心定位

### 1.1 为什么需要这个支柱？

AI Coding的落地,最终不是技术问题,而是**组织能力问题**。

```
个人会用AI ≠ 团队会用AI
短期试点成功 ≠ 长期规模化应用
工具部署完成 ≠ 能力真正沉淀
```

这个支柱解决的核心问题：

```
如何将个人的AI使用经验,转化为团队的资产和能力?
如何建立持续改进的机制,而不是一次性项目?
```

### 1.2 与成熟度模型的关系

**重要说明**：

| 文档 | 定位 | 范围 |
|------|------|------|
| **企业级AI-Coding成熟度模型V2.0** | 企业级AI Coding全能力成熟度 | 覆盖所有支柱的L1-L5评估 |
| **支柱6-组织能力演进** | 仅聚焦组织维度的能力建设 | 从成熟度模型中提取组织相关内容 |

**支柱6不是成熟度模型的重复,而是聚焦于**：
- 知识资产沉淀(Skill/Memory)
- 培训体系完善
- 跨团队协作机制
- 持续改进闭环

## 二、知识资产沉淀

### 2.1 Skill资产化

**Skill库架构**：

```
skills/
├── common/                    # 通用Skill(架构组维护)
│   ├── generate-feature       # 功能实现
│   ├── fix-bug                # Bug修复
│   ├── write-test             # 单元测试
│   └── code-review            # 代码审查
├── domain/                    # 领域Skill(域负责人维护)
│   ├── order-processing       # 订单处理
│   ├── payment                # 支付
│   ├── inventory              # 库存
│   └── user-management        # 用户管理
└── team/                      # 团队定制Skill(Tech Lead维护)
    ├── deploy-script          # 部署脚本
    ├── data-migration         # 数据迁移
    └── performance-tuning     # 性能调优
```

**Skill沉淀流程**：

```
个人发现有效Prompt
  ↓
封装为Skill模板
  ↓
团队内部验证(至少3个项目使用)
  ↓
提交到Skill库(代码Review)
  ↓
上架到Skill Hub(全员可用)
  ↓
持续收集反馈(调用率×采纳率)
  ↓
低效Skill下架或优化
```

**Skill质量评估**：

| 指标 | 说明 | 目标值 |
|------|------|--------|
| **调用率** | 被使用的次数 | >100次/月 |
| **采纳率** | 生成代码被合并的比例 | >70% |
| **满意度** | 用户评分 | >4.0/5.0 |
| **维护频率** | 更新周期 | <90天 |

### 2.2 Memory分层体系

**四层Memory架构**：

```
组织级Memory(CTO/架构组维护)
├── 技术战略
├── 架构原则
├── 技术栈选型
└── 合规要求

团队级Memory(Tech Lead维护)
├── 团队编码规范
├── 常用设计模式
├── 领域知识
└── 最佳实践

项目级Memory(项目经理维护)
├── 项目Spec
├── 接口文档
├── 部署配置
└── 已知问题

会话级Memory(开发者维护)
├── 当前任务上下文
├── 临时决策记录
└── 个人笔记
```

**Memory更新机制**：

```yaml
memory_update_rules:
  # 组织级：季度更新
  organization:
    frequency: quarterly
    owner: 架构委员会
    review_process: 技术委员会评审
    
  # 团队级：月度更新
  team:
    frequency: monthly
    owner: Tech Lead
    review_process: 团队内部分享
    
  # 项目级：迭代更新
  project:
    frequency: per-iteration
    owner: 项目经理
    review_process: 迭代回顾会议
    
  # 会话级：实时更新
  session:
    frequency: real-time
    owner: 开发者个人
    review_process: 自我管理
```

### 2.3 知识中台建设

**知识类型占比**：

| 类型 | 占比 | 说明 | 示例 |
|------|------|------|------|
| **物料文档** | 60-70% | 内部组件API、用法示例 | ProTable使用指南 |
| **经验知识** | 20-30% | 踩坑记录、技术决策 | 分布式锁踩坑经验 |
| **开发规范** | 5-10% | 按域的编码规范 | 订单域编码规范 |

**知识检索场景**：

| 阶段 | 检索内容 | 典型用例 |
|------|---------|---------|
| **G3** | 业务知识 | 虚拟商品识别规则 |
| **G5** | 技术规范 | BusinessException用法 |
| **G6** | 代码模式 | ProTable cacheKey约束 |

**知识质量保障**：

```yaml
knowledge_quality:
  # 自动评估
  auto_metrics:
    - 调用率 × 采纳率 < 20% → 标记为低效知识
    - 90天无调用 → 标记为过期知识
    - 用户评分 < 3.0 → 标记为待优化
    
  # 人工审核
  manual_review:
    frequency: monthly
    reviewers: 领域专家
    actions:
      - 更新过期内容
      - 合并重复知识
      - 删除无用知识
```
