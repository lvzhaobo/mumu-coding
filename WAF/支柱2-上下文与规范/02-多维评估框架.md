# AI 代码质量多维评估框架

## 核心洞察

> **约束悖论**：给 AI 的约束越多，代码越符合团队风格，但 AI 的"自由发挥空间"被压缩，
> 在某些维度上的表现可能反而下降。评估体系必须捕捉到这个此消彼长的关系。

```
                    AI 自由发挥质量
高 ┤  ★ G1
   │      ★ G2
   │          ★ G3
   │              ★ G4
   │                 ★ G5
   │                    ★ G6
低 ┤
   └──────────────────────────→ 约束程度

                    团队风格符合度
高 ┤                    ★ G6
   │                 ★ G5
   │             ★ G4
   │         ★ G3
   │     ★ G2
   │  ★ G1
低 ┤
   └──────────────────────────→ 约束程度

                    综合生产可用性（我们真正要的）
高 ┤                    ★ G6
   │                ★ G5
   │            ★ G4
   │        ★ G3
   │    ★ G2
   │ ★ G1
低 ┤
   └──────────────────────────→ 约束程度
```

**关键论点**：G1 生成的代码可能"看起来不错"，甚至用了很优雅的设计模式，
但放到客户项目中是**不可用的**——因为风格不对、架构不对、接口不对。
"生产可用性"才是最终衡量标准，而非"代码好不好看"。

## 评估维度定义（5 个维度）

### 维度一：代码生成质量（AI 自由发挥水平）

> 不考虑团队约束，单纯看代码本身的技术水平

| 评分项 | 说明 |
|--------|------|
| 架构设计合理性 | 分层是否清晰、职责是否单一、依赖关系是否合理 |
| 代码简洁度 | 是否冗余、是否过度设计、复杂度是否合理 |
| 设计模式运用 | 是否恰当使用设计模式（而非滥用） |
| 代码可读性 | 变量命名是否自解释、逻辑是否清晰 |
| 测试完备性 | 是否生成了测试、覆盖率如何 |

**G1 在这个维度可能得分不低**，因为 AI 会使用"教科书式"的最佳实践。
比如可能会用策略模式处理三种场景、用 Builder 模式创建对象——代码很优雅，
但这些模式未必是客户团队的习惯。

**预期趋势**：G1 ≈ G2 > G3 ≈ G4 ≈ G5 ≈ G6（约束多了，AI 没法自由选择最优方案）

---

### 维度二：团队风格符合度

> 代码"看起来像团队写的"程度

| 评分项 | 说明 |
|--------|------|
| 命名风格一致性 | 类名/方法名/变量名是否与团队现有代码一致 |
| 分层架构一致性 | 包结构、分层方式是否与项目一致 |
| 异常处理模式 | 是否使用团队的异常体系（BusinessException） |
| 日志格式一致性 | 日志级别、格式是否与团队规范一致 |
| 工具使用一致性 | ORM、工具类的使用方式是否与团队一致 |
| 代码组织方式 | 方法内部的代码组织、注释风格是否与团队一致 |

**G1 在这个维度必然很低**，因为完全没有参照。
**G6 在这个维度最高**，因为有明确的规范和参考代码。

**预期趋势**：G1 < G2 < G3 < G4 < G5 << G6（G5→G6 有跳升，因为有了真实代码参照）

---

### 维度三：业务正确性

> 是否正确理解并实现了业务逻辑

| 评分项 | 说明 |
|--------|------|
| 核心流程正确性 | 三个场景（A/B/C）的处理流程是否正确 |
| 业务规则准确度 | 虚拟商品识别、拆单规则、发货逻辑是否正确 |
| 边界条件覆盖 | 是否处理了特殊情况（多个虚拟商品、并发等） |
| 异常场景处理 | API 失败、拆单异常等是否有合理处理 |
| 业务概念理解 | "中台"、"问题单"、"无物流发货"等概念是否正确理解 |

**G1 在这个维度会很差**——"中台"、"拆单"、"问题单"这些领域概念，
AI 可能会按字面意思理解或根据通用知识猜测，偏差很大。

**G3 开始有明显提升**——详细的规则定义让 AI 不需要猜测。

**这个维度揭示了一个关键事实**：G1 的代码再优雅，如果业务逻辑是错的，就是废代码。

**预期趋势**：G1 << G2 < G3 < G4 ≈ G5 ≈ G6（G3 是业务正确性的关键拐点）

---

### 维度四：生产可用性

> 代码拿到客户项目中，不改/少改就能用的程度

| 评分项 | 说明 |
|--------|------|
| 能否直接编译通过 | 放到项目中编译是否报错 |
| 能否直接运行 | 依赖是否完整、配置是否正确 |
| 与现有系统兼容性 | 是否使用了现有的公共类、是否会破坏现有功能 |
| 人工修改量 | 达到上线标准需要修改多少行 |
| 数据模型兼容性 | 表结构是否与现有系统匹配 |

**这是最能说明"AI 实际价值"的维度。**

G1 的代码虽然可能很优雅，但放到客户项目中大概率编译都过不了——
因为它自己定义了 Result 类、自己设计了表结构、自己发明了异常体系，
和客户现有系统完全不兼容。

**预期趋势**：G1 << G2 < G3 < G4 < G5 < G6（约束越多，生产可用性越高）

---

### 维度五：可维护性

> 后续团队成员能否轻松理解和维护这段代码

| 评分项 | 说明 |
|--------|------|
| 其他开发者可理解性 | 新人能否快速看懂代码意图 |
| 配置化程度 | 业务规则是否硬编码、是否支持动态修改 |
| 可扩展性 | 新增场景（如拼多多平台）是否容易扩展 |
| 日志可排查性 | 出了问题能否通过日志快速定位 |
| 监控可观测性 | 是否有关键指标可以监控 |

**G1 可能在可扩展性上做得不错**（AI 喜欢用设计模式），
但在日志可排查性和监控上做得很差（不知道团队的日志和监控规范）。

**预期趋势**：非线性，G1 和 G6 可能各有优劣

## 预期得分对比矩阵

| 维度 | G1 | G2 | G3 | G4 | G5 | G6 |
|------|----|----|----|----|----|----|
| **代码生成质量** | 3.5 | 3.3 | 3.2 | 3.2 | 3.0 | 3.0 |
| **团队风格符合** | 1.0 | 1.5 | 2.0 | 2.2 | 3.8 | 4.5 |
| **业务正确性** | 1.5 | 2.5 | 3.8 | 4.2 | 4.2 | 4.3 |
| **生产可用性** | 0.5 | 1.5 | 3.0 | 3.5 | 3.8 | 4.3 |
| **可维护性** | 2.5 | 2.5 | 3.0 | 3.3 | 3.5 | 4.0 |

### 趋势可视化

```
5分 ┤
    │  ┌─── 代码生成质量（随约束增加略有下降）
4分 ┤  │         ┌─── 团队风格（随约束增加持续上升）
    │  ↓        │
3分 ┤ ===---____│____          ╱──── 团队风格
    │           │        ╱───╱
2分 ┤           │   ╱───╱
    │           ╱──╱
1分 ┤      ╱───╱
    │ ____╱
0分 ┤
    └────┬────┬────┬────┬────┬────
         G1   G2   G3   G4   G5   G6

关键发现：
- 代码生成质量：缓慢下降（AI 被约束后无法自由发挥）
- 团队风格：持续上升（约束越多越符合）
- 两条线的交叉点大约在 G3-G4 之间
- 综合来看，G3 之后的总分是上升的
```

## 权重设计：对客户来说什么最重要？

### 场景一：客户关注"AI 能不能替代开发"（侧重生产可用性）

| 维度 | 权重 |
|------|------|
| 代码生成质量 | 10% |
| 团队风格符合 | 20% |
| 业务正确性 | 30% |
| **生产可用性** | **30%** |
| 可维护性 | 10% |

→ 这个权重下 G6 >> G1，结论明确

### 场景二：客户关注"AI 代码到底好不好"（侧重技术质量）

| 维度 | 权重 |
|------|------|
| **代码生成质量** | **30%** |
| 团队风格符合 | 10% |
| 业务正确性 | 25% |
| 生产可用性 | 15% |
| 可维护性 | 20% |

→ 这个权重下 G1 的排名会上升，但仍然不如 G5/G6

### 场景三：推荐的平衡权重

| 维度 | 权重 | 理由 |
|------|------|------|
| 代码生成质量 | 15% | 有价值但不是最重要的 |
| 团队风格符合 | 20% | 团队协作的基础 |
| 业务正确性 | 25% | 代码最终要解决业务问题 |
| 生产可用性 | 25% | 决定 AI 的实际 ROI |
| 可维护性 | 15% | 长期价值 |

## 如何向客户呈现"约束悖论"

### 讲故事的方式

> "我们发现一个有趣的现象：不给 AI 任何约束时，它写出的代码反而
> 在某些指标上得分更高——架构更'优雅'、设计模式运用更'教科书'。
>
> 但这就像请了一个技术很强的外包，他用了最新的技术栈和最优雅的设计，
> 却和你们团队的代码风格完全不同，融不进现有项目。
>
> 真正有价值的 AI 代码，不是'最好的代码'，而是'最适合你们项目的代码'。
> 这就是为什么 Spec 和编码规范如此重要——它们不是在限制 AI，
> 而是在帮 AI 把能力用在正确的地方。"

### 用数据说话

```
G1 的代码生成质量得分：3.5/5 （看起来不错）
G1 的生产可用性得分：0.5/5 （但完全不能用）
G1 的人工修改率：    >70%  （基本要重写）

G6 的代码生成质量得分：3.0/5 （略低于 G1）
G6 的生产可用性得分：4.3/5 （几乎可以直接用）
G6 的人工修改率：    <15%  （微调即可上线）
```

**结论**：G1 "看起来好"但"不能用"，G6 "看起来普通"但"直接能用"。
你选哪个？

## 评估执行方法

### 自动化指标（客观）

| 指标 | 工具 | 对应维度 |
|------|------|---------|
| 编译通过率 | Maven/Gradle build | 生产可用性 |
| 单元测试通过率 | JUnit | 业务正确性 |
| 测试覆盖率 | JaCoCo | 代码生成质量 |
| Lint 错误数 | Checkstyle | 代码生成质量 |
| 静态缺陷数 | SonarQube/SpotBugs | 代码生成质量 |
| 圈复杂度 | SonarQube | 可维护性 |
| 代码重复率 | SonarQube | 代码生成质量 |
| 人工修改行数 | git diff | 生产可用性 |

### 人工评审指标（主观）

| 指标 | 评审方式 | 对应维度 |
|------|---------|---------|
| 风格一致性打分 | 盲审评分表 | 团队风格符合 |
| 业务逻辑正确性 | AC 逐项检查 | 业务正确性 |
| 架构合理性 | 架构师评审 | 代码生成质量 |
| 可理解性 | 随机抽 1 名开发者阅读 | 可维护性 |
| "像不像团队写的" | 盲审猜测来源 | 团队风格符合 |

### 特殊评估项："来源猜测测试"

> 把 6 组代码匿名后，让评审人猜测每份代码是 AI 写的还是人工写的。
>
> - G1 大概率一眼就被识别为 AI（风格太"教科书"了）
> - G6 的目标是让评审人**猜不出来**
>
> "猜错率"本身就是一个非常直观的指标。

## 直觉类比：命题作文 vs 自由作文

> 用教育场景的类比，让非技术背景的人也能秒懂"约束与质量"的关系。

### 作文类比对照表

| 作文类比 | AI Coding 对应 | 特点 |
|----------|---------------|------|
| **自由作文**："写一篇关于春天的文章" | **G1**：裸需求直接生成 | AI 自由发挥，可能写得很华丽，但不是老师要的 |
| **半命题作文**："写春天，要求包含三个场景" | **G2**：简单 Spec | 有了方向约束，但细节自由 |
| **命题作文**："以《春归》为题，800字，议论文，必须引用..." | **G3**：完整 Spec | 主题、结构、内容都有明确要求 |
| **命题作文 + 评分标准公开** | **G4**：Spec + Checklist | 知道怎么打分，就知道往哪里发力 |
| **命题作文 + "请模仿朱自清的风格"** | **G5**：Spec + 编码规范 | 有了风格约束 |
| **命题作文 + "参考这篇范文的写法"** | **G6**：Spec + 规范 + 参考代码 | 有了具体模仿对象 |

### 核心规律：约束越多，方差越小，下限越高

**自由作文得高分 ≠ 命题作文得高分。**

一个学生自由作文可能写得天马行空、文采飞扬（类似 G1 的代码很"优雅"），
但给他一个命题作文，要求模仿朱自清的风格，他反而可能得分更低——
因为**约束越多，出彩的空间越小，但跑题的风险也越小**。

```
G1（自由作文）：上限可能高，但下限极低，方差极大
G6（命题作文）：上限被约束了，但下限很高，方差极小

对企业来说，要的不是"偶尔惊艳"，而是"稳定可用"。
```

### 写诗的类比：约束的更高维度

如果说写散文是"基础开发"，那写诗就是"在存量系统上做改造"——约束维度更多：

| 约束层级 | 作文类比 | AI Coding 类比 |
|----------|---------|---------------|
| 内容约束 | 写"春天" | 实现"虚拟商品自动发货" |
| 结构约束 | 写"议论文" | 使用"Controller-Service-Mapper 分层" |
| 形式约束 | 写"七言律诗" | 使用"团队的异常处理模式、日志格式" |
| 风格约束 | 模仿"李白的风格" | 模仿"团队现有代码的风格" |
| 韵律约束 | "平仄押韵" | "命名规范、代码格式" |

**写诗比写散文难**，因为要同时满足内容+格式+韵律+意境。
同理，在现有系统上写出风格一致的代码，比从零写一个新项目难得多——约束维度更多。

### Workshop 开场话术建议

> "让 AI 自由写代码，就像让学生写自由作文——可能写得很漂亮，但不是你要的。
>
> 我们做的事情，就是帮你把'自由作文'变成'命题作文'——
> 告诉 AI 题目是什么、结构怎么写、风格模仿谁。
>
> 约束越清晰，AI 交出的答卷越稳定、越可用。
>
> 今天的 Workshop 就是用数据证明：每增加一层约束，代码质量提升多少。"
