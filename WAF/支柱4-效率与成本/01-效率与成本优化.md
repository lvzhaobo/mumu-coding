# 支柱4：效率与成本 (Efficiency & Cost)

> 优化AI使用的投入产出比和资源利用效率

---

## 一、核心定位

### 1.1 为什么需要这个支柱？

AI Coding不是免费的。每次调用都消耗Token,每次返工都浪费时间。

这个支柱解决的核心问题：

```
投入：时间(准备Prompt) + 成本(Token消耗) + 人力(审查修改)
产出：代码质量 + 交付速度 + 团队效率

问题：如何让投入产出比最大化？
```

### 1.2 效率链条

```
任务拆分(怎么做)
  ↓
Prompt工程(怎么问)
  ↓
Token效率(怎么省)
  ↓
并行处理(怎么快)
  ↓
ROI度量(怎么算)
```

**这不是割裂的几个点,而是一个完整的效率链条。**

## 二、任务拆分策略

### 2.1 为什么任务拆分是效率的前提？

**因果关系链**：

```
任务拆分不合理
  ↓
一次性给AI超大需求(比如"实现整个订单系统")
  ↓
Prompt必然模糊、上下文必然超载
  ↓
AI输出质量下降 → 需要多次返工
  ↓
Token浪费 + 人工修改时间增加
  ↓
效率降低 + 成本上升
```

**反过来的正向逻辑**：

```
合理拆分任务(每次<300行改动)
  ↓
Prompt可以写得很具体、上下文聚焦
  ↓
AI一次输出质量高 → 减少返工
  ↓
Token精准消耗 + 人工微调即可
  ↓
效率提升 + 成本下降
```

### 2.2 任务拆分原则

| 原则 | 说明 | 实际案例 |
|------|------|---------|
| **单次改动<300行** | 超过300行容易失控 | "实现虚拟商品识别"(150行) vs "实现整个订单系统"(2000行) |
| **职责单一** | 每个任务只解决一个问题 | "识别虚拟商品" vs "识别+拆单+发货"(三个任务) |
| **接口先行** | 先定义接口,再实现逻辑 | 先写API Spec,再写Service实现 |
| **依赖解耦** | 减少任务间的依赖 | 先完成公共模块,再并行开发业务模块 |

### 2.3 复杂任务分解方法论

**WBS分解法(Work Breakdown Structure)**：

```
需求：实现虚拟商品自动处理系统

L1分解：
├─ 1. 虚拟商品识别模块
├─ 2. 订单拆单模块
├─ 3. 自动发货模块
└─ 4. 日志监控模块

L2分解(以模块1为例)：
├─ 1.1 虚拟商品配置管理(CRUD)
├─ 1.2 虚拟商品识别算法
├─ 1.3 识别结果缓存
└─ 1.4 单元测试

L3分解(以1.2为例)：
├─ 1.2.1 关键字匹配函数
├─ 1.2.2 ID清单匹配函数
├─ 1.2.3 综合判定函数
└─ 1.2.4 边界条件测试
```

## 三、Prompt工程效率

### 3.1 结构化Prompt模板库

**模板1：Spec驱动编码**

```markdown
## 任务
实现[功能名称]

## 关联Spec
- Spec文档：[SPEC-XXX-功能说明.md]
- 验收标准：AC1-AC5
- 测试用例：TC001-TC006

## 技术要求
- 技术栈：[Java 17 + Spring Boot 3.2 + MyBatis-Plus]
- 包路径：[com.smartmall.virtual]
- 编码规范：[参见AGENTS.md]

## 约束条件
- 使用现有的Result<T>、BusinessException(不要重新定义)
- 可注入调用现有的OrderService、ProductService
- 不要重新实现已有功能

## 输出要求
- 完整的Service实现类
- 对应的单元测试(覆盖率>80%)
- 关键逻辑的代码注释
```

**模板2：Bug修复**

```markdown
## 问题描述
- 现象：[具体错误信息]
- 复现步骤：[步骤1→步骤2→步骤3]
- 期望行为：[应该怎样]
- 实际行为：[实际怎样]

## 定位信息
- 日志：[关键日志片段]
- 相关文件：[VirtualProductService.java:125]
- 可能原因：[初步分析]

## 修复要求
- 修复Bug,不要引入新功能
- 保持现有接口不变
- 添加回归测试用例
```

### 3.2 Prompt复用率提升方法

**方法1：建立Prompt模板库**

```
.qoder/
└── prompts/
    ├── feature-impl.md       # 功能实现模板
    ├── bug-fix.md            # Bug修复模板
    ├── refactoring.md        # 重构模板
    ├── unit-test.md          # 单元测试模板
    └── code-review.md        # 代码审查模板
```

**方法2：使用Skill封装**

```bash
# /skill generate-feature --spec=SPEC-2026-001

# Skill内部逻辑：
# 1. 读取Spec文档
# 2. 读取AGENTS.md编码规范
# 3. 加载功能实现模板
# 4. 自动生成结构化Prompt
```

**方法3：无效对话识别与优化**

```yaml
# 无效对话特征
invalid_conversation_patterns:
  - pattern: "请重新生成"  # 重复生成
    reason: "Prompt不够具体"
    action: "优化Prompt,增加约束条件"
    
  - pattern: "不是这个意思"  # 理解偏差
    reason: "业务规则描述不清"
    action: "补充Spec细节或提供参考代码"
    
  - pattern: "换个方案"  # 多次尝试
    reason: "需求不明确"
    action: "先澄清需求,再生成代码"
```

### 3.3 无效对话占比目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| **无效对话占比** | <10% | 10轮对话中,无效对话不超过1轮 |
| **一次通过率** | >70% | AI首次生成的代码,70%以上无需修改 |
| **平均修改次数** | <2次 | 达到满意质量,平均修改不超过2次 |

## 四、Token成本管理

### 4.1 Token消耗监控与预警

**监控维度**：

| 维度 | 说明 | 工具 |
|------|------|------|
| **按用户** | 每个开发者的Token消耗 | Qoder Dashboard |
| **按项目** | 每个项目的Token消耗 | 项目统计 |
| **按场景** | 开发/测试/运维的Token消耗 | 场景标记 |
| **按模型** | 不同模型的Token消耗对比 | 模型选择记录 |

**预警阈值**：

```yaml
token_alerts:
  daily_limit: 100000  # 每日上限
  warning_threshold: 80%  # 80%时预警
  critical_threshold: 100%  # 100%时告警
  
  alert_channels:
    - email
    - slack
    - 钉钉
```

### 4.2 模型选型成本对比

| 场景 | 推荐模型 | Token成本(每千Token) | 质量得分 | 性价比 |
|------|---------|---------------------|---------|--------|
| **简单任务** | 轻量级模型 | ¥0.01 | 3.5/5 | ★★★★★ |
| **复杂逻辑** | 标准模型 | ¥0.03 | 4.2/5 | ★★★★ |
| **核心架构** | 高级模型 | ¥0.06 | 4.5/5 | ★★★ |
| **代码审查** | 标准模型 | ¥0.03 | 4.0/5 | ★★★★ |
| **Bug修复** | 高级模型 | ¥0.06 | 4.3/5 | ★★★ |

**优化策略**：

```
简单任务用轻量模型(便宜)
复杂任务用高级模型(精准)
避免"一刀切"都用最贵的模型
```

### 4.3 上下文窗口优化策略

**问题**：上下文窗口越大,Token消耗越多。

**优化方法**：

| 方法 | 说明 | 节省效果 |
|------|------|---------|
| **精准引用** | 只引用相关文件,不引用整个项目 | 节省60-70% |
| **分层加载** | 先加载概要,按需加载细节 | 节省40-50% |
| **缓存复用** | 重复的Spec/规范缓存使用 | 节省30-40% |
| **清理无关上下文** | 移除不相关的历史对话 | 节省20-30% |

## 五、并行处理与自动化

### 5.1 多任务并行模式

**Quest委托模式**：

```
主任务：实现虚拟商品自动处理系统
├─ Quest 1：虚拟商品识别模块(开发者A)
├─ Quest 2：订单拆单模块(开发者B)
├─ Quest 3：自动发货模块(开发者C)
└─ Quest 4：日志监控模块(开发者D)

并行执行,互不依赖
预计完成时间：从12天缩短到4天(提升67%)
```

**适用场景**：

| 场景 | 是否可并行 | 说明 |
|------|-----------|------|
| 独立模块开发 | ✅ | 模块间接口已定义 |
| 单元测试编写 | ✅ | 与开发并行 |
| 文档编写 | ✅ | 与代码开发并行 |
| 数据库设计 | ❌ | 需要先完成,其他模块依赖 |
| 核心架构设计 | ❌ | 需要先完成,指导后续开发 |

### 5.2 Skill资产复用机制

**Skill库建设**：

```
skills/

    ├── code-review-checklist  # 代码审查清单
```

**复用率目标**：

| 指标 | 目标值 | 说明 |
|------|--------|------|
| **Skill/模板复用率** | >60% | 60%以上的任务使用现有Skill/模板 |
| **新Skill开发周期** | <1天 | 从需求到可用不超过1天 |
| **Skill覆盖率** | >80% | 80%以上的常见任务有对应Skill |

## 六、ROI度量体系

### 6.1 效率提升计算

**投入产出对比**：

```
G1→G6的投入产出分析：
───────────────────────────────────────────────────────────────
G1:  5分钟  → 1.5分  → 人工修改率 >70%  → 基本不可用
G6: 5小时   → 4.5分  → 人工修改率 <12%  → 直接可用

ROI: 每投入1小时准备约束,节省5-8小时人工修改时间
```

**效率提升公式**：

```
效率提升 = (传统开发时间 - AI辅助开发时间) / 传统开发时间 × 100%

示例：
传统开发：实现虚拟商品识别 = 3天
AI辅助：
  - Spec准备：2小时
  - AI生成：30分钟
  - 审查修改：1小时
  - 测试验证：1小时
  总计：4.5小时 ≈ 0.5天

效率提升 = (3 - 0.5) / 3 × 100% = 83%
```

### 6.2 成本效益分析

**成本构成**：

| 成本项 | 说明 | 占比 |
|--------|------|------|
| **AI工具成本** | Qoder订阅费、API调用费 | 15% |
| **学习成本** | 培训时间、试错成本 | 20% |
| **基础设施** | CI/CD资源、服务器 | 10% |
| **人力成本** | Spec编写、代码审查 | 55% |

**收益构成**：

| 收益项 | 说明 | 占比 |
|--------|------|------|
| **开发效率提升** | 编码时间缩短 | 50% |
| **返工成本降低** | Bug减少、质量提升 | 25% |
| **新人上手加速** | 培训时间缩短 | 15% |
| **知识沉淀价值** | Skill/模板复用 | 10% |

### 6.3 投资回报追踪

**ROI计算公式**：

```
ROI = (收益 - 投入) / 投入 × 100%

示例：
年度投入：
  - AI工具：¥50万
  - 培训：¥20万
  - 基础设施：¥10万
  总计：¥80万

年度收益：
  - 效率提升节省人力：¥120万
  - 返工成本降低：¥40万
  - 新人培训成本降低：¥20万
  总计：¥180万

ROI = (180 - 80) / 80 × 100% = 125%
```
