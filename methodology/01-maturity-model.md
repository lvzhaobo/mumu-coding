## 1. 问题定义

企业在评估自身 AI Coding 成熟度时，面临以下系统性问题 [1]：

| 角色 | 典型判断 | 偏差来源 |
|------|---------|---------|
| 一线工程师 | "我们每天都在用 AI 写代码" | 将工具使用率等同于能力成熟度 |
| 技术架构师 | "团队没有统一的编码规范" | 感知到问题但缺乏量化基线 |
| CTO / 技术 VP | 被问及时无法给出确定答案 | 缺乏可汇报的结构化评估框架 |
| 业务管理层 | "再试两个项目看看" | 没有判断标准来决策投入规模 |

**核心问题：同一组织内部，不同角色对成熟度的判断可能相差 2-3 个级别。** 这种认知偏差导致战略决策建立在未经校准的主观判断之上。

E-ACMM 的设计目标是将"感觉"转化为可度量的指标，提供一套跨角色通用的评估语言。

## 2. 模型结构

```
5 级 × 6 维度 × 30 题
```

### 2.1 五级定义

级别的数量设计遵循一个原则：**级别数 = 质变点个数 + 1**。AI Coding 在企业落地有四个必须跨越的分水岭，加上起点，合为五级。

| 级别 | 名称 | 定义 | 典型停留时长（估算） |
|------|------|------|-------------------|
| **L1** | 个人探索 | AI 编码活动仅发生在个人层面，组织层面无可见投入 | 起点 |
| **L2** | 企业试点 | 有书面授权和试点团队，产出初步资产，但未跨团队推广 | 2-6 个月 |
| **L3** | 全面使用 | 规范进入正式版本管理，过半工程师日常使用，能力嵌入组织流程 | 6-18 个月 |
| **L4** | 量化驱动 | 建立度量体系，数据进入管理层决策，出现过数据驱动的战略调整 | 18-36 个月 |
| **L5** | 研发范式 | 方法论被外部引用，核心资产被独立复现，组织输出行业标准 | 持续演进 |

> 停留时长为**估算值**，基于 30+ 企业的实践观察 [1]。实际周期因组织规模、行业类型和管理层投入程度而异。

**四组质变点：**
1. L1→L2：从个人到组织 — 书面合规 + 首批资产入库
2. L2→L3：从试点到全面 — 能力嵌入组织骨架，不依赖特定个体
3. L3→L4：从经验到数据 — 指标进入管理层决策议程
4. L4→L5：从跟随到定义 — 外部组织引用你的方法论

### 2.2 六大评估维度

E-ACMM 使用与 WAF 一致的六维度作为评估支柱：

| 维度 | 名称 | 评估重点 |
|------|------|---------|
| **D1** | 意图传递 | Spec 质量、需求管理流程、变更控制机制 |
| **D2** | 工具连通 | MCP 接入、权限模型、环境隔离 |
| **D3** | 流程嵌入 | 代码评审嵌入、测试自动化、质量门禁 |
| **D4** | 知识沉淀 | AGENTS.md、Rules、ADR、知识复用机制 |
| **D5** | 治理闭环 | 安全基线、ROI 度量、合规追溯链 |
| **D6** | 组织演进 | 试点规模化、讲师认证、责任归属 |

## 3. 评估铁律

### 铁律一：短板原则

> 组织成熟度级别由**最弱的维度**决定，不取平均值，不取最突出项。

**工程含义：** 若某组织在 D1-D5 均达到 L3 标准，但 D6（组织演进）仅处于 L1，则整体级别为 L2，而非 L3。

该原则的实践价值在于防止"亮点效应"——用某一个维度的优异表现掩盖其他维度的不足。在成熟度评估中最常见的误判是"取平均"——组织在五个维度得分很高、一个维度得分很低，对外宣称"我们平均 L3"。短板原则直接堵死了这个后门。

### 铁律二：门禁验证

> 晋级必须同时满足**硬事实**和**硬指标**，且可被第三方核验。

| 验证类型 | 示例 | 不符合项 |
|---------|------|---------|
| 硬事实 | 管理层评审会议纪要中记录了因数据推翻原有判断 | "团队积极性很高" |
| 硬指标 | PR-Spec 关联率连续 8 周 ≥ 70% | "AI 使用率在提升" |
| 第三方可核验 | 可在 Git、PR、会议纪要、指标仪表盘中查到 | 周报中的描述性表述 |

主观感受、定性形容词、未落地的计划，均不纳入评估。门禁验证的设计初衷是：E-ACMM 需要成为一个**可信的评估工具**，而不是一个**自我感觉良好的镜子**。

## 4. 各级典型特征

### L1 · 个人探索

**定义：** AI 编码活动处于无组织状态，管理层不可见。

**典型表现：**
- 工程师自费订阅工具，使用行为对组织不可见
- 无书面合规政策，无预算科目
- 产出物未入库，绑定在个人工作环境
- 知识传递依赖私信和口头交流

**晋级 L2 的门禁：** 书面合规许可 + 首批资产入库 + 纳入预算

### L2 · 企业试点

**定义：** 有组织的试点项目，但能力未跨团队扩散。

**典型表现：**
- 有授权、预算和试点团队
- 产出初版规范文件（如 AGENTS.md 初版）
- 试点团队数据良好（如效率提升 30%）
- 跨团队推广受阻，其他团队观望
- ROI 说不清，预算每季度需重新论证

**风险提示：** L2 是最容易长期滞留的级别。试点数据良好与跨团队推广失败并存是典型特征，滞留时间可达 18 个月以上 [1]。

**晋级 L3 的门禁：** 跨团队可复用资产 ≥ 3 个 + 正式版规范 + 过半工程师日常使用

### L3 · 全面使用

**定义：** AI Coding 能力嵌入组织研发流程，规范进入正式版本管理。

**典型表现：**
- 规范通过正式评审流程，有版本管理
- 过半工程师将 AI 编码工具纳入日常工作流
- 数据采集体系建立（使用率、产出质量、效率指标）
- 管理层知晓投入但尚未基于数据做决策

**定位：** 多数企业的合理目标终点。L3 意味着 AI Coding 不再是"某个试点团队的事"，而是组织的基础能力。

**晋级 L4 的门禁：** 数据进入管理层季度评审议程 + 至少一次数据驱动的决策调整记录

### L4 · 量化驱动

**定义：** 度量数据真正影响组织决策。不是"我们采集了数据"，而是"数据改变过决策"。

**典型表现：**
- 管理层评审会议中，数据推翻或修正了原有判断
- ROI 指标成为预算论证的依据
- 不同团队/项目的数据被横向比较，驱动资源配置
- 方法论被外部机构（咨询公司、行业协会）引用

**特征：** 全球范围内处于该级别的组织数量有限 [1]。

**晋级 L5 的门禁：** 方法论被外部独立引用 + 核心资产被外部组织复现

### L5 · 研发范式

**定义：** 组织从方法论消费者转变为方法论输出者。

**典型表现：**
- 组织开发的规范、工具、流程被外部引用
- 参与或主导行业标准制定
- 核心方法论资产被独立于本组织的外部团队复现和应用
- 持续自我更新机制运行

**定位：** 无终点状态，维持靠持续更新。

## 5. 行业基准参考

基于多个行业的企业培训和咨询数据 [1]：

| 行业 | 集中级别 | 说明 |
|------|---------|------|
| 制造业 / 传统零售 / 政务国企 | L1，少量 L2 | 起步阶段，工具采纳有限 |
| 金融 / 银行 | L2 为主，少量 L3 | 合规要求驱动规范意识 |
| 头部互联网 / 科技公司 | L2-L3，极少数 L4 | 工具到位但组织变革不足 |
| AI 原生公司 | L3-L4，极少数 L5 | AI 融入组织基因 |

> 行业分布为估算，样本量 30+ 企业，不构成统计结论。读者所在行业的分布可能与此表有差异。

## 6. 常见误判

| 误判 | 诊断 |
|------|------|
| "Copilot 覆盖率 90%" | 覆盖率 ≠ 成熟度。L2 的门禁是书面合规 + 可复用资产，不是安装率 |
| "我们有 AGENTS.md" | 初版 AGENTS.md 不等于正式版规范。L3 要求经过评审、版本管理、跨团队一致 |
| "试点团队效率提升 30%" | L2 不卡在试点数据，卡在跨团队推广。单点数据好 ≠ 成熟度达标 |
| "我们有 ROI 数据" | 自说自话的 ROI 不满足门禁要求。L4 要求数据经得起第三方核验且影响过决策 |
| "我们团队很积极" | 主观感受不纳入评估。硬事实 + 硬指标 + 可核验，缺一不可 |

## 7. 评估方法

### 自评流程

1. 逐题评估，选择最符合当前状态的选项（A-E）
2. 6 个维度分别计分
3. 以**最低分维度**对应的级别作为整体级别

### 评分维度

每题五个选项分别对应 L1 至 L5：

| 选项 | 含义 | 对应级别 |
|------|------|---------|
| A | 未开展 / 完全不具备 | L1 |
| B | 个人层面尝试，无组织推动 | L1-L2 |
| C | 初步规范，覆盖部分团队 | L2 |
| D | 规范正式化，覆盖大部分团队 | L3 |
| E | 数据驱动，持续优化，被外部引用 | L4-L5 |

### 配套工具

- **30 题在线自评问卷**：[在线版](../canvas/knowledge-hub/ai-coding-maturity.html) | [H5 自评页面](maturity-assessment.html)
- **完整白皮书**（~10000 字）：每级详细解读 + 8 条晋级门禁 + 行动路线图
- **在线雷达图**：[成熟度诊断工具](../canvas/knowledge-hub/ai-coding-maturity.html)

## 8. 与其他框架的关系

本模型在 SDAC 体系中的角色：**定位**——回答"我的团队在哪一级"。

```
成熟度模型（定位：我在哪一级）
       │
       ▼
  WAF 六维度（诊断：各维度在哪一级）
       │
       ▼
  Landing Zone（行动：先铺设哪层地基）
       │
       ▼
  G-Ladder（方向：下一步能力往哪升级）
```

| 框架 | 定位 | 与 E-ACMM 的关系 |
|------|------|--------------|
| E-ACMM | **定位**——当前所处级别 | 本框架 |
| WAF | **诊断**——六维度分别的成熟度分布 | E-ACMM 的细化诊断工具 |
| Landing Zone | **行动**——按优先级铺设地基 | 从 L1→L2 的落地路径 |
| G-Ladder | **方向**——能力升级路径 | 每级的"下一步"具体化为 G-Ladder 的级别跃迁 |

## 9. 与行业模型的区别

E-ACMM 度量的对象是 **AI Coding 的组织能力**，而非软件工程过程的整体质量。它与现有模型互补：

| 模型 | 度量对象 | 与 E-ACMM 的关系 |
|------|---------|-----------------|
| **CMMI** | 软件过程成熟度 | 互补。E-ACMM L3 门禁包含 CMMI 级别的过程管理要求 [2] |
| **DORA** | 交付与运维效能（4 项指标） | 互补。E-ACMM L4 门禁中 DORA 四项为必要条件 [3] |
| **E-ACMM** | AI Coding 的组织能力成熟度 | 独立维度，可与 CMMI、DORA 联合使用 |

三者可并行评估。L4 组织应在 CMMI、DORA、E-ACMM 三个维度上分别达到对应级别。

## 10. 已知局限

1. **验证状态**：E-ACMM 目前处于经验验证阶段（30+ 企业使用），尚未经过心理测量学的信度和效度检验。分数可靠性依赖评估者的诚实度和对标准的理解。
2. **样本偏斜**：行业分布数据来自 30+ 家企业样本，以中型企业（50-500 研发人员）为主。超大型企业和初创公司的代表性不足。
3. **自评偏差**：自评天然存在高估倾向。"短板原则"设计的目的之一就是对抗这种偏差，但无法完全消除。
4. **行业适配**：当前 30 题通用版对所有行业使用相同的评估维度。金融、医疗等强合规行业可能需要增加行业专用评估项。
5. **动态变化**：AI Coding 工具和最佳实践的演进速度极快。本模型的各级门禁标准可能需要每 6-12 个月重新校准。
