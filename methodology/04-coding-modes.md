## 1. 问题定义

企业 AI Coding 实践中存在一个系统性偏差：培训体系倾向于教授"最佳实践"（Spec-Driven），但实际代码库中仅 10-20% 的产出需要完整的 Spec 流程[^6]。

对所有代码施加同等流程约束的后果：

| 症状 | 根因 |
|------|------|
| 团队对 AI Coding 产生抵触 | 简单任务被过度流程化 |
| 规范文件与实际执行脱节 | 流程要求超出实际需要 |
| AI Coding 的实际收益被流程成本抵消 | 投入产出比倒挂 |

本框架提供一套基于工程特征的决策模型，帮助团队在不同场景下选择适当的编码模式。

## 2. 五种编码模式

### 2.1 Vibe Coding

**定义：** 人通过自然语言描述意图，AI 直接生成代码，人通过交互迭代满意后结束。

| 属性 | 值 |
|------|-----|
| 需求形式 | 隐式（对话中逐步明确） |
| 代码评审 | 事后快速审查 |
| 变更追溯 | 无 |
| 适用生命周期 | < 3 个月 |
| 适用团队规模 | 1 人 |
| 合规适用性 | 不适用 |

**适用条件（需同时满足）：**
1. 产出不需要长期维护
2. 单人开发，无协作需求
3. 出错成本可接受（可随时重写）
4. 无合规或审计要求

**风险：** 基于行业数据，不加约束的 Vibe Coding 在第 3 个月后技术债累积速度超过人工偿还能力。该模式本质上是"接受短期效率换取长期技术债"的权衡。

### 2.2 Glue Coding

**定义：** 按接口定义和数据映射关系，由 AI 生成集成胶水代码。

| 属性 | 值 |
|------|-----|
| 需求形式 | 接口文档 + 数据映射表 |
| 代码评审 | 重点验证接口调用和数据转换 |
| 变更追溯 | 轻量 |
| 适用生命周期 | 中等（取决于上游接口稳定性） |
| 适用团队规模 | 1-3 人 |
| 合规适用性 | 低 |

**关键工程原则：** 接口定义的质量决定产出质量。将接口文档作为主要输入，AI 负责生成 boilerplate 代码和异常处理逻辑。

### 2.3 TDD（Test-Driven Development）

**定义：** 人编写测试用例，AI 实现通过测试的代码。测试用例本身即为最精确的需求规格。

| 属性 | 值 |
|------|-----|
| 需求形式 | 测试用例（可执行、可验证） |
| 代码评审 | 测试覆盖率 + 边界条件 |
| 变更追溯 | 中等 |
| 适用生命周期 | 长期 |
| 适用团队规模 | 1-5 人 |
| 合规适用性 | 中 |

**工程优势：** 测试用例消除了需求的歧义性。AI 的工作目标是"让这些测试通过"——这是一个无歧义、可验证的目标，天然适合 AI 执行。

### 2.4 Spec Coding

**定义：** 人编写 Spec 文档，AI 按 Spec 生成代码。Spec 是跨角色协作的唯一共识源。

| 属性 | 值 |
|------|-----|
| 需求形式 | 完整的 Spec 文档（至少 04+06+09+14） |
| 代码评审 | 先评审 Spec，Spec 通过后才评审代码 |
| 变更追溯 | 完整（RTM 双向追溯） |
| 适用生命周期 | 长期 |
| 适用团队规模 | 3+ 人 |
| 合规适用性 | 高 |

**工程价值：**
1. 需求变更通过 Spec 传递，影响可自动分析
2. Spec 作为团队的唯一真相源，消除信息差
3. AI 的输入空间被 Spec 限定，消除猜测空间

### 2.5 Harness Coding

**定义：** 多 Agent 按预定义工作流编排执行，人在关键节点进行审批。编码只是工作流中的一个环节。

| 属性 | 值 |
|------|-----|
| 需求形式 | 14 文档 + 工作流定义 + 审批规则 |
| 代码评审 | AI Review + 人工审批双保险 |
| 变更追溯 | 最完整（全链路日志） |
| 适用生命周期 | 长期 + 高可靠性要求 |
| 适用团队规模 | 5+ 人 |
| 合规适用性 | 最高 |

**三层恢复机制：**

| 风险等级 | 触发条件 | 恢复策略 |
|---------|---------|---------|
| LOW | 代码风格问题 | Agent 自动重试 |
| MEDIUM | 逻辑错误 | Checkpoint 回滚 + 重新生成 |
| HIGH / CRITICAL | 架构或安全问题 | Human-in-the-loop 阻断，人工介入 |

**核心原则：Harness 的关键不在"用多个 Agent"，在于"在正确的位置设置人的审批节点"。**

## 3. 决策模型

### 3.1 决策树

```
代码需要维护超过 3 个月吗？
├── 否 ─────────────────────────────────→ Vibe Coding
└── 是 → 协作人数？
    ├── 1 人 → 涉及外部服务集成？
    │   ├── 是 ─────────────────────────→ Glue Coding
    │   └── 否 → 是算法 / 核心逻辑？
    │       ├── 是 ─────────────────────→ TDD
    │       └── 否 ─────────────────────→ Spec Coding
    └── 3+ 人 → 代码库规模？
        ├── < 10 万行 ──────────────────→ Spec Coding
        └── ≥ 10 万行 → 有合规 / 安全要求？
            ├── 是 ─────────────────────→ Harness Coding
            └── 否 ─────────────────────→ Spec Coding + Agentic 增强
```

### 3.2 决策对照表

| 判断条件 | 对应模式 |
|---------|---------|
| 生命周期 < 3 个月 + 单人 | Vibe |
| 需要集成第三方服务 | Glue |
| 算法 / 核心业务逻辑，正确性优先 | TDD |
| 团队 3+ 人协作，长期维护 | Spec |
| 合规要求或代码库 ≥ 10 万行 | Harness |

## 4. 组合应用

实际项目中，五种模式**共存**：

```
电商项目示例：
├── 营销活动页面    → Vibe（原型 → 上线后即废弃）
├── 支付集成        → Glue（调用微信 / 支付宝 SDK）
├── 推荐算法        → TDD（核心逻辑，正确性优先）
├── 订单管理模块    → Spec（8 人团队，长期维护）
└── 风控系统        → Harness（合规要求，多 Agent 审核）
```

### 典型企业代码库的模式分布

| 模式 | 估算占比 | 工程含义 |
|------|---------|---------|
| Vibe | ~15% | 原型、工具脚本、临时分析 |
| Glue | ~20% | 集成层、数据管道、ETL |
| TDD | ~15% | 核心算法、关键业务逻辑 |
| Spec | ~30% | 生产功能、团队协作产出 |
| Harness | ~10% | 关键系统、合规场景 |
| 其他 | ~10% | 文档、配置 |

> 以上分布基于对 30+ 企业代码库的观察估算，非统计样本。实际分布因行业和团队规模而异。

## 5. 常见误解

| 误解 | 纠正 |
|------|------|
| "Spec 是最佳实践，所有代码都应该用 Spec" | 反过来的。80% 的代码不需要 Spec。Spec 应用于 20% 需要它的场景 |
| "Vibe Coding 就是不规范" | Vibe Coding 是**接受短期效率换取技术债**的主动选择，不是"做不到 Spec" |
| "Glue Coding 太简单，不值得专门学习" | Glue 代码占企业代码库 20%，且是最容易出安全问题的类型（第三方依赖变更、证书过期） |
| "Harness 就是用更多 Agent" | Harness 的核心是**人在关键节点的审批机制**，Agent 数量不是衡量标准 |
| "TDD 和 AI 不兼容" | AI + TDD 是天然组合。AI 最擅长"让测试通过"——这是一个无歧义的可验证目标 |

## 8. 已知局限

1. **模式分布为经验值**：五种模式在企业代码库中的占比分布（Vibe ~15%、Spec ~30% 等）基于 30+ 企业的观察 [^6]，非统计样本。实际分布因行业和团队规模而异。
2. **Harness 模式实践不足**：Harness Coding 是本体系中实践案例最少的模式。多数企业尚未到达需要多 Agent 编排的阶段。该模式的定义主要基于对 Anthropic"Building Effective Agents" [1] 等公开资料的分析，而非一手实践。
3. **TDD + AI 的适配尚未充分验证**：TDD 与 AI 的组合在理论上是最佳实践（测试用例即精确 Spec），但在实践中，AI 在"理解测试意图"上仍存在偏差。该模式的推荐基于逻辑推理而非大量对照实验。
4. **决策树不覆盖所有边缘场景**：三个问题（生命周期、协作人数、代码规模）覆盖了 80% 的场景，但特殊场景（如"高安全要求的小项目"、"大量非功能性约束的简单功能"）可能不在决策树覆盖范围内。
5. **模式名称的稳定**性："Vibe Coding"、"Spec-Driven" 等术语在行业中仍在快速演化。本文档中的定义基于 2026 年 6 月的行业共识，未来 12 个月内部分术语可能发生变化。
