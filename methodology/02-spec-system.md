## 1. 定义

Spec 是一套由 14 份文档组成的工程规约体系，覆盖从需求采集到上线追溯的全流程。每份文档有明确的输入、输出、责任人和填写规范。

**设计目标：**
1. 作为人机共同的工作契约——人定义需求，AI 按 Spec 执行，代码反过来验证 Spec 完整性
2. 实现需求变更的可追溯——RTM（追溯矩阵）自动分析变更影响链
3. 支撑多人协作的共识机制——Spec 是跨角色、跨团队的唯一真相源
4. 满足合规与审计要求——14 文档天然形成完整审计链路

## 3. 各文档内容结构

### 3.1 上游文档（Meta + Proposal）

**01 写作总则** — 整套 Spec 的"语法书"

| 章节 | 内容 |
|------|------|
| 1. 目的 | 定义本套 Spec 的服务对象和使用场景 |
| 2. 受众 | 列出所有会阅读 Spec 的角色（PM、开发、QA、架构师、安全） |
| 3. 术语表 | 项目中使用的专有名词定义 |
| 4. 格式规范 | 文档结构、命名约定、语言风格 |
| 5. 版本控制 | 文档如何版本化、评审、打 tag |
| 6. AI 辅助规范 | AI 工具解读 Spec 的指令 |

**02 需求采集** — 原始需求的来源整理

| 章节 | 内容 |
|------|------|
| 1. 需求来源 | 业务方、用户反馈、竞品分析、合规要求等 |
| 2. 干系人清单 | 每个干系人的角色、诉求、决策权限 |
| 3. 业务背景 | 为什么这个需求重要，不做的后果 |
| 4. 初步假设 | 当前对需求的假设，需后续验证 |

**03 立项提案** — 项目级决策依据

| 章节 | 内容 |
|------|------|
| 1. 执行摘要 | 一段话说明项目内容和价值 |
| 2. 问题陈述 | 当前的问题是什么，影响多大 |
| 3.  proposed 方案 | 高层级的解决思路 |
| 4. 范围界定 | 包含什么、不包含什么 |
| 5. 成功标准 | 可度量的验收指标 |
| 6. 时间线与里程碑 | 关键节点和交付物 |
| 7. 风险评估 | 风险矩阵（可能性 × 影响 × 缓解措施） |
| 8. 干系人签批 | 各角色审批记录 |

**04 产品需求（PRD）** — 功能级需求定义

| 章节 | 内容 |
|------|------|
| 1. 产品概述 | 产品/功能是什么，为谁服务 |
| 2. 用户画像 | 典型用户角色及其核心诉求 |
| 3. 功能清单 | 功能 ID、描述、优先级、状态 |
| 4. 用户旅程 | 主要流程和边缘场景 |
| 5. 业务规则 | 每条规则的触发条件和执行动作 |
| 6. 数据需求 | 需要什么数据、来源、格式、量级 |
| 7. 集成点 | 需要对接的外部系统 |
| 8. 高层验收标准 | 怎么判断功能"做完" |

### 3.2 核心文档（Spec + Design）

**05 用户故事** — 需求到开发的翻译层

| 章节 | 内容 |
|------|------|
| 1. 故事清单 | 作为[角色]，我想要[功能]，以便[价值] |
| 2. 验收条件（AC） | 每个故事的可验证完成标准 |
| 3. 优先级排序 | MoSCoW 方法（Must/Should/Could/Won't） |
| 4. 依赖关系 | 故事间的依赖和阻塞关系 |

**06 功能规格（FSD）** — 开发者的直接输入

| 章节 | 内容 |
|------|------|
| 1. 功能概述 | 本功能解决什么问题 |
| 2. 交互流程 | 每一步的界面、操作、系统响应 |
| 3. 界面说明 | 页面布局、组件、交互细节 |
| 4. 异常处理 | 每种异常情况的处理方式 |
| 5. 状态机 | 功能涉及的状态和流转 |
| 6. 边界条件 | 输入范围、时间限制、并发处理 |

**07 非功能需求（NFR）** — 质量的底线

| 章节 | 内容 |
|------|------|
| 1. 性能要求 | 响应时间、吞吐量、并发数 |
| 2. 可用性要求 | SLA、容灾、备份策略 |
| 3. 安全性要求 | 认证、授权、数据保护 |
| 4. 兼容性要求 | 浏览器、设备、系统版本 |
| 5. 可维护性要求 | 监控、日志、可观测性 |

**08 架构选型** — 技术决策记录

| 章节 | 内容 |
|------|------|
| 1. 架构概述 | 整体架构图和设计原则 |
| 2. 技术选型 | 每个技术选型的选项对比和决策理由 |
| 3. 关键决策（ADR） | 重要决策的架构决策记录 |
| 4. 部署架构 | 环境、部署方式、扩容策略 |
| 5. 依赖关系 | 内部依赖和外部依赖 |
| 6. 风险与权衡 | 选型的代价和替代方案 |

**09 API 契约** — 前后端并行开发的依据

| 章节 | 内容 |
|------|------|
| 1. API 概览 | Base URL、版本、认证方式、格式 |
| 2. 端点详述 | 每个端点的请求/响应格式、错误码 |
| 3. 通用模型 | 跨端点共享的数据结构 |
| 4. 错误格式 | 统一的错误响应结构 |
| 5. 追溯 | 每个端点关联的用户故事和 AC |

**10 数据模型** — 数据的结构定义

| 章节 | 内容 |
|------|------|
| 1. 实体关系图 | ER 图或等效的结构描述 |
| 2. 表结构 | 每个表的字段、类型、约束 |
| 3. 索引策略 | 索引设计及其理由 |
| 4. 数据流 | 数据在系统中的流转路径 |
| 5. 迁移方案 | 数据迁移或初始化的方案 |

**11 安全设计** — 安全工程的规约

| 章节 | 内容 |
|------|------|
| 1. 攻击面分析 | 系统的所有入口和可能的攻击路径 |
| 2. 权限模型 | 角色、权限、访问控制策略 |
| 3. 数据安全 | 加密、脱敏、传输安全 |
| 4. 安全控制 | 输入验证、输出编码、安全头 |
| 5. 审计与日志 | 需要记录的操作和日志格式 |
| 6. 合规映射 | 满足哪些合规要求（等保、GDPR 等） |

### 3.3 执行与验证（Plan + Test + Trace）

**12 实施计划** — 项目执行蓝图

| 章节 | 内容 |
|------|------|
| 1. 里程碑 | 关键节点和交付物 |
| 2. 任务分解 | WBS，每个任务的负责人和预估工时 |
| 3. 依赖关系 | 任务间的依赖和关键路径 |
| 4. 风险矩阵 | 识别、评估、缓解措施 |
| 5. 回滚方案 | 每个里程碑的回滚策略 |

**13 测试策略** — 质量的保障计划

| 章节 | 内容 |
|------|------|
| 1. 测试范围 | 测什么、不测什么 |
| 2. 测试策略 | 单元/集成/E2E/性能/安全的策略 |
| 3. 测试环境 | 环境配置和测试数据方案 |
| 4. 通过标准 | 各阶段的准入和准出标准 |
| 5. 自动化策略 | 哪些测试自动化、工具选型 |
| 6. 追溯 | 每个测试用例关联的需求和 AC |

**14 追溯矩阵（RTM）** — 全链路的双向追溯

| 章节 | 内容 |
|------|------|
| 1. 完整矩阵 | 需求 → PRD → 用户故事 → FSD → API → 数据 → 测试 |
| 2. 覆盖率汇总 | 每类文档的追溯完成率 |
| 3. 缺口与风险 | 未覆盖的需求及其影响 |
| 4. 变更日志 | 每次变更的记录和影响 |

## 4. 分级管理

并非每次变更都需要走完 14 份文档。按影响程度分级：

| 级别 | 名称 | 判定标准 | 所需流程 | 占比 |
|------|------|---------|---------|------|
| **L1** | 轻量级 | 单团队、单一组件、低回滚成本 | 口头共识 | ~50% |
| **L2** | 标准级 | 2-3 个团队、单一服务、中等回滚成本 | 一次对齐会（30min） | ~40% |
| **L3** | 重量级 | 4+ 团队、跨服务影响、高回滚成本 | 完整文档 + 门禁验证 | ~10% |

### L2 对齐会流程

```
会前（15 分钟）：
  变更方准备：改什么、为什么、预估影响范围

会议（30 分钟）：
  参会方：PM + 开发负责人 + QA
  议程：确认变更内容 → 确认受影响文档 → 确认更新责任人 → 确认时间线

会后（自动）：
  更新相关 Spec 文档
  PR 关联 Spec 编号
  RTM 自动记录变更链路
```

## 5. Spec 冻结机制

冻结 = Spec 从"草稿"进入"受控变更"状态。

### 冻结时机

| 时机 | 冻结范围 | 原因 |
|------|---------|------|
| 迭代开始前 | 当轮次 03-13 | 防止 Scope Creep |
| 发布前 | 全部 14 份 | 合规审计需要 |
| 重大变更前 | 受影响文档 | 变更影响分析的基线 |

### 变更流程

```
1. 提交变更请求
   内容：目标 Spec 编号、变更原因、影响范围

2. 影响评估
   RTM 自动分析 + 文档责任人确认
   输出：受影响文档清单

3. 审批
   L1：变更方自行决定
   L2：对齐会确认
   L3：完整评审流程

4. 更新 Spec → 重新冻结 → 代码按新 Spec 更新
```

## 8. Spec Skills：AI 辅助 Spec 工程

本仓库配套 11 个 Spec Skills，用于在 Cursor IDE 中自动化 Spec 的编写、维护、验证流程。按功能分为三类：

### 8.1 内容生成（7 个 Skill）

| Skill | 调用方式 | 功能 |
|-------|---------|------|
| **spec-coding-14** | `@spec-coding-14` | 总控：选择轮次、执行铁律、OpenSpec 分工 |
| **spec-elicit-02** | `@spec-elicit-02` | 原始素材 → 02 需求采集文档 |
| **spec-round1-proposal** | `@spec-round1-proposal` | R1：02 → 03 立项提案 + 04 PRD |
| **spec-round2-anchor** | `@spec-round2-anchor` | R2：05 用户故事 ↔ 09 API 契约 |
| **spec-round3-design** | `@spec-round3-design` | R3：08 架构 + 10 数据模型 → 06 FSD + 07 NFR + 11 安全 |
| **spec-round4-close** | `@spec-round4-close` | R4：12 实施计划 + 13 测试策略 → 14 追溯矩阵 |

**四轮工作流：**
```
R1（提案轮）：02 需求采集 → 03 立项提案 → 04 PRD
R2（锚定轮）：05 用户故事 ↔ 09 API 契约（双向对齐）
R3（设计轮）：08 架构 + 10 数据 → 06 FSD + 07 NFR + 11 安全
R4（收口轮）：12 实施计划 + 13 测试策略 → 14 追溯矩阵
```

### 8.2 维护（2 个 Skill）

| Skill | 调用方式 | 功能 |
|-------|---------|------|
| **spec-sync-on-change** | `@spec-sync-on-change` | 修改一份 Spec 后，自动联动更新相关文档 |
| **spec-impact-blast-radius** | `@spec-impact-blast-radius` | 变更前扫描：报告受影响文档、测试用例、爆炸半径指数 |

### 8.3 版本与流程（3 个 Skill）

| Skill | 调用方式 | 功能 |
|-------|---------|------|
| **spec-doc-versioning** | `@spec-doc-versioning` | 文稿版次管理、Approved 状态、Git tag、变更记录 |
| **spec-openspec-lifecycle** | `@spec-openspec-lifecycle` | 完整生命周期：propose → 写 Spec → validate → apply → archive |
| **spec-validate-gates** | `@spec-validate-gates` | 发布/归档前的文档侧门禁检查 |

### 8.4 推荐工作流

**新项目：**
```
spec-elicit-02 → round1 → round2 → round3 → round4
→ spec-validate-gates → spec-doc-versioning（打 tag）
```

**增量变更：**
```
openspec propose <name>
→ spec-impact-blast-radius（可选：先出影响面报告）
→ spec-sync-on-change（按报告执行联动）
→ spec-validate-gates（终检）
→ 代码实现
→ archive + spec-doc-versioning + git commit
```

## 9. 快速上手

### 第一次使用 Spec

**最小可用集（推荐从这 4 份开始）：**

| 优先级 | 文档 | 作用 |
|--------|------|------|
| 1 | 01 写作总则 | 定义团队的 Spec 规范 |
| 2 | 03 立项提案 | 项目级决策依据 |
| 3 | 04 产品需求（PRD） | 功能级需求定义 |
| 4 | 14 追溯矩阵 | 建立变更追溯基线 |

### 使用模板

1. 从 [specs/templates/](../specs/templates/) 复制对应模板
2. 按模板中的章节逐项填写
3. 填写完成后使用 `@spec-validate-gates` 检查门禁
4. 通过后打 Git tag 标记版本

### AI 辅助

使用 Cursor IDE 的 Spec Skills（见第 8 节），通过 `@spec-coding-14` 总控 Skill 启动四轮工作流，AI 将引导你逐份完成 Spec 文档的编写。

---

## 10. 已知局限

1. **14 份文档并非所有场景都必要**：三分级机制的存在正是为了解决这一问题。实际使用中，团队应根据项目特征裁剪文档集，而非机械套用全部 14 份。
2. **文档维护成本**：Spec 体系的有效性依赖持续维护。冻结后长期不更新的 Spec 会产生误导——AI 会基于过时的 Spec 生成代码。建议至少每两个迭代周期审查一次 Spec 的有效性。
3. **AI 工具适配**：不同 AI 编码工具对 Spec 的"消费能力"不同。某些工具能直接解析 Spec 的结构化字段，某些则需要人工将 Spec 内容作为对话上下文注入。本文档中的"AI 按 Spec 执行"是一个理想化描述，实际效果因工具而异。
4. **非技术团队的接受度**：PM 角色在 Spec 体系中被要求承担更多的结构化写作工作。在非技术导向的组织中，这可能遇到阻力。建议从 03 立项提案和 04 PRD 开始逐步引入，而非一次性要求全部 14 份。
5. **Spec 与代码的同步延迟**：冻结机制要求"改代码前先改 Spec"，这在紧急 Hotfix 场景下可能是一种负担。需要在流程中定义紧急通道——事后补 Spec 的例外机制。
