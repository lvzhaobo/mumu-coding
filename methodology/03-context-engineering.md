## 1. 定义

Context Engineering（CE）是 Prompt Engineering（PE）的扩展：

| | Prompt Engineering | Context Engineering |
|--|-------------------|---------------------|
| 关注点 | 单条提示词的质量 | AI 消费的**全部上下文**的质量 |
| 范围 | 一句话 / 一个 prompt | 上下文窗口内的所有内容 |
| 优化目标 | 让单次请求更准确 | 让持续交互更稳定、更可预测 |

**核心公式：**

```
输出质量 = f(模型能力, 上下文质量)
```

在模型能力趋同的背景下（各主流模型基准差距持续缩小），上下文质量成为最后的差异化因素。

[^4]: Anthropic, "Effective Context Engineering for AI Agents" (2025). 核心观察：尽管 AI 编码工具普及率持续增长，但绝大多数用户仅使用基础功能，未能充分利用上下文工程的高级能力。

## 2. 四层上下文模型

企业环境中的上下文分布在四个层次，每层对应一类治理问题：

| 层次 | 内容范围 | 管理工具 | 典型问题 |
|------|---------|---------|---------|
| **项目级** | 代码结构、依赖关系、技术栈版本 | CLAUDE.md / .cursorrules / Steering | AI 无法完整理解项目结构，生成代码引用不存在的模块 |
| **团队级** | 编码规范、评审标准、命名约定 | Rules 文件、Spec 模板 | 不同团队使用同一工具但产出风格不一致 |
| **组织级** | 安全策略、合规要求、内部知识库 | RAG 系统、内部知识平台 | AI 不知道内部 API 存在，建议调用外部等效服务 |
| **历史级** | 架构决策理由、踩坑记录、演进路径 | ADR（Architecture Decision Records）、Git 历史注释 | AI 建议已被验证过的失败方案，新人重复踩坑 |

### 每层的工程问题

**项目级 — 入口问题：**
```
症状：AI 生成的代码 import 了项目中不存在的模块
根因：AI 未能加载完整的项目结构和依赖声明
治理：在 CLAUDE.md 中维护项目级上下文快照
```

**团队级 — 一致性问题：**
```
症状：同一工具在不同团队产出的代码风格差异显著
根因：缺少团队级的输出约束文件
治理：Rules 文件 + Spec 模板标准化
```

**组织级 — 可达性问题：**
```
症状：AI 不知道公司有内部 API 网关，建议直接调用外部支付接口
根因：内部系统不在模型的训练数据中
治理：MCP Server 将内部系统能力暴露为结构化接口
```

**历史级 — 遗忘问题：**
```
症状：AI 推荐方案 X，但团队两年前评估 X 时已排除
根因：决策历史未结构化记录
治理：ADR 文件 + Git 历史注释
```

## 3. Context Rot：上下文衰减

LLM 的注意力机制存在固有的衰减特性——上下文窗口内的信息并非等权处理。

### 三症状

| 症状 | 表现 | 根因 |
|------|------|------|
| **早期准确，后期幻觉** | 长对话中，前半部分回答准确，后半部分开始产生事实性错误 | 注意力在长序列中分散 |
| **窗口间不一致** | 同一仓库在不同对话窗口中，AI 行为差异显著 | 上下文加载顺序和裁剪策略不同 |
| **团队成员产出差异大** | 同一工具，A 工程师产出质量 80 分，B 工程师产出 40 分 | A 的 CLAUDE.md / Rules / MCP 配置完整，B 的配置缺失 |

### 根因分类

| 根因 | 机制 | 治理策略 |
|------|------|---------|
| 容量超限 | 上下文窗口满后，关键信息被新消息挤出 | 分层上下文——最重要信息置顶/置底 |
| 信息过时 | 旧规范仍存在于上下文中，新规范未同步 | 版本化管理 + 过期清理机制 |
| 信息冗余 | 同一规则在多个位置重复，消耗 token 预算 | 单一信息源，引用替代复制 |
| 噪声污染 | 调试日志、历史对话占用上下文空间 | 定期裁剪，保留核心上下文 |

## 4. 六层约束递进模型

从代码结构到测试断言，逐层注入约束——每层解决一类确定的问题：

```
┌────────────────────────────────────────────────────────┐
│  L6  测试断言     用测试用例约束输出正确性             │
│  L5  MCP / 工具   用外部工具扩展能力边界               │
│  L4  AGENTS.md    用角色定义约束行为边界               │
│  L3  规则定义     用编码规范约束输出风格               │
│  L2  文件组织     用目录结构约束搜索范围               │
│  L1  代码结构     用清晰结构降低理解起点               │
└────────────────────────────────────────────────────────┘
```

| 层级 | 约束内容 | 解决的问题 | 典型工具 | 到达率（估算）[^5] |
|------|---------|-----------|---------|-------------|
| L1 | 代码结构 | AI 理解项目的入口 | 清晰的目录结构 + 包声明文件 | 高 |
| L2 | 文件组织 | AI 搜索和引用的范围 | 按功能分层目录 + README | 高 |
| L3 | 规则定义 | AI 的输出风格和质量 | .cursorrules / CLAUDE.md | 中 |
| L4 | AGENTS.md | AI 的角色和行为边界 | AGENTS.md + 角色定义 | 中低 |
| L5 | MCP / 工具 | AI 的能力边界 | MCP Server + SKILL | 低 |
| L6 | 测试断言 | AI 输出的正确性 | 单元测试 + 集成测试 + E2E | 中 |

**关键洞察：六层是递进依赖关系，非并列关系。**

- L1 是基础——代码结构混乱时，后续所有层效果递减
- L2 是导航——让 AI 高效定位相关文件
- L3-L4 是规则层——定义"怎么做"
- L5 是扩展层——接入外部系统能力
- L6 是验证层——用代码约束代码

## 5. 工具配置规范

### AGENTS.md

AI Agent 的角色定义文件，包含以下要素：

| 要素 | 内容 | 示例 |
|------|------|------|
| 角色定义 | Agent 的身份和职责 | "你是这个项目的 AI 编程助手" |
| 能力清单 | Agent 可执行的操作范围 | 读写代码、运行测试、查阅文档 |
| 行为边界 | Agent 不可执行的操作 | 不直接提交 main 分支、不删除未 tracked 文件 |
| 工作流程 | 标准操作流程 | 读 Spec → 写代码 → 跑测试 → 提交 PR |
| 输出规范 | 输出格式和详细程度 | 代码注释语言、PR 描述格式 |

### Rules

团队级编码规范和 AI 使用规则：

| 要素 | 内容 |
|------|------|
| 命名约定 | 文件、变量、函数的命名规范 |
| 代码风格 | 缩进、注释、格式化标准 |
| 架构约束 | 分层规则、依赖方向、禁止跨越的边界 |
| AI 使用规范 | 何时用 Spec、何时直接编码、Review 标准 |

### MCP（Model Context Protocol）

将外部系统和数据源以标准化协议暴露给 AI Agent：

```
AI Agent ←→ MCP ←→ 内部系统
                         ├── 数据库查询接口
                         ├── 内部 API 目录
                         ├── 知识库检索
                         └── 代码仓库
```

**工程价值：** MCP 将"组织级上下文"转化为 AI 可消费的结构化数据，消除 AI 因信息缺失导致的错误建议。

## 6. 注意力预算模型

上下文窗口是有限资源，其分配是技术决策：

**类比：** 工程师 8 小时工作日中，若 6 小时用于无效会议，剩余 2 小时写代码——产出不会高。上下文窗口同理。

### 建议分配

| 内容类型 | 建议占比 | 说明 |
|---------|---------|------|
| 项目结构 + 核心依赖 | 15% | 一次加载，全会话受益 |
| 当前任务 Spec | 20% | 每次会话的核心输入 |
| 团队规则 + 编码规范 | 10% | 标准化输出的基础 |
| 相关历史（ADR / 近期 PR） | 15% | 避免重复踩坑 |
| 工具定义（MCP / SKILL） | 10% | 扩展 AI 能力 |
| 对话历史 + 调试信息 | 30% | 自然累积，需定期裁剪 |

## 7. 与其他框架的关系

| 框架 | 关系 |
|------|------|
| 成熟度模型 | P2（上下文与记忆）是成熟度评估的核心维度 |
| Spec 体系 | Spec 是上下文中优先级最高的单一文件——无 Spec 的上下文工程是无靶射击 |
| G-Ladder | L2 需要 Rules，L3 需要 Spec + AGENTS.md，L4 需要 MCP，L5 需要 RAG——上下文工程是 G-Ladder 的技术基础 |
| WAF | P2 支柱 = 上下文工程在企业治理层的落地 |
| 编码模式 | Spec / Harness 模式对上下文质量要求最高 |

## 9. 已知局限

1. **理论基础处于演进中**：Context Engineering 作为独立领域刚刚兴起。本文档中提出的六层约束递进模型和注意力预算模型是基于实践观察的归纳，尚未经过实验验证 [^5]。
2. **六层约束是理想模型**：现实中，团队很难完整实施 L5（MCP）和 L6（测试断言）。L1-L4 是当前实践中最常见的落地范围。高层级约束的投入产出比需要更多案例数据支撑。
3. **上下文大小与质量的权衡**：本文档强调"最小可行上下文"，但实践中很难一刀切地判断"什么是最小"。不同项目类型的最优上下文大小可能有显著差异。
4. **工具依赖**：AGENTS.md 和 MCP 的配置方式因 AI 编码工具而异。本文档中的配置示例偏向通用描述，具体实现需参考各工具的官方文档。
5. **Context Rot 诊断依赖经验**：目前没有自动化的 Context Rot 检测工具。诊断主要依赖团队对"AI 输出质量下降"的主观感知。
